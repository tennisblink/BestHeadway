Developer note — how to add a new rule
Rule functions live in M5 (module5_simulation.html). Rule definitions (names, descriptions, groups) live here in M6. Both must be updated together when adding a new rule — the rule ID is the link between them.

Step 1 — Add the rule function to M5

In module5_simulation.html, add a function following the standard interface:

function ruleYOUR_RULE_ID(ctx) {
  // ctx = { train_id, trainState, ilState, ilConfig, params,
  //         allTrainStates, resourceMap, turnoutRegistry,
  //         requestedRouteId }
  //
  // Must return:
  return {
    allow:            true | false,   // false = block route request
    ma_ch:            number | null,  // MA chainage override (MA rules only)
    ma_reason:        string,         // reason code for log
    blocked_by_train: string | null,  // train causing the block
    waiting_for:      string,         // human-readable resource description
    sideEffects:      [],             // lockPoint / releasePoint mutations
    warnings:         []              // non-fatal messages
  };
}

Then register it in the IL_RULES object:

const IL_RULES = {
  // ... existing rules ...
  'YOUR_RULE_ID': ruleYOUR_RULE_ID   // ← add this line
};

Step 2 — Add the rule definition to M6

In module6_interlocking_*.html, add an entry to the RULE_DEFS array:

{
  id:         'YOUR_RULE_ID',         // must match IL_RULES key in M5 exactly
  name:       'Human-readable name',
  desc:       'What this rule does and when it applies.',
  group:      'group_key',            // internal grouping key
  groupLabel: 'Group Label',          // displayed in UI section header
  phase:      'request',              // request | always | release | ma
  execOrder:  60,                     // controls order within phase; lower = earlier
  impl:       'full',                 // full | partial | stub
  defaultOn:  false,                  // pre-ticked on first load?
  mutexGroup: null                    // string key if mutually exclusive with others,
                                      // null if independent
}

Phase reference

Phase When it runs Typical use
requestWhen train triggers route requestTrack occupancy, point locking, overlap check
alwaysEvery tick for every running trainEarly point release, continuous checks
releaseWhen train exits route or sectionSectional release, full route release
maEvery tick — computes MAMA to route end, MA to fouling point
